# Proposal

## Why

The workspace rule says synthetic traffic sent to any deployed environment
must carry `X-Greeter-Synthetic: true`. Two tools in this repo don't send it:

- `bin/smoke`, which `cd.yml` runs after every dev deploy, every prod deploy
  and every dev restore. Each run greets a new `smoke guest <hex>` twice and
  sends one malformed request.
- `perf/load.rb`, the deployed load generator used by `perf/http_bench.rb`
  when `GREETER_BASE_URL` is set. At its defaults (25 req/s for 60 s), one run
  greets about 1,500 distinct `perf guest <vu>-<n>` names.

Without the header these greetings land under real `GUEST#` keys. They show
up in real counts and in `synthetic = false` log lines, and their counter
items never expire. The `adopt-acceptance-gate` change recorded the
`bin/smoke` gap as design finding S10 and deferred it to a separate change
("make `bin/smoke` send `X-Greeter-Synthetic: true`"). This is that change,
extended to the load generator, which has the same gap.

## What Changes

- `bin/smoke` sends `X-Greeter-Synthetic: true` on every request, including
  the malformed-JSON check.
- `GreeterHttp::Perf::Load` sends `X-Greeter-Synthetic: true` on every
  request.
- A new `synthetic-traffic` capability with one requirement: tools in this
  repo that send traffic to a deployed stage mark it as synthetic. It has one
  scenario per tool.
- Two new RSpec files, one per scenario, tagged with the requirement and
  scenario slugs.
- `docs/observability.md` lists `bin/smoke` and the load generator as
  synthetic traffic sources next to the canary.

The service's response to these requests doesn't change, because the marker
doesn't alter responses (`version-headers` requirement "Synthetic marker does
not alter version headers or responses"). The `bin/smoke` count check still
works because synthetic counts increment in the same way.

## Capabilities

### New Capabilities

- `synthetic-traffic`: how traffic generated by this repo's own tools against a
  deployed stage is marked, so it stays out of real guest counts and
  real-user log views.

### Modified Capabilities

None.

## Impact

- **Repos:** greeter-http only. greeter-core isn't affected.
  greeter-acceptance isn't changed. Its gate traffic belongs to that repo.
- **Edited files:** `bin/smoke`, `perf/load.rb`, `docs/observability.md`.
- **New files:** `spec/bin/smoke_spec.rb`, `spec/perf/load_spec.rb` and the
  change's spec delta.
- **Unchanged (constraint):** `lib/`, `infra/`, `openapi.yaml`, every
  workflow under `.github/workflows/`, every feature file and step
  definition.
- **Deploy behaviour:** after the change, CD's `bin/smoke` runs write
  `synthetic#GUEST#…` items instead of `GUEST#…` items. Prod
  still gets about three POSTs per run.
- New files under `spec/` mean the maintainer runs `tests-open` for the red
  commit.

## Non-goals

- No cleanup of `smoke guest …` or `perf guest …` items already written under
  real `GUEST#` keys. Removing them is a manual data operation on prod. It
  needs its own decision and a PITR backup point first.
- No change to how the service reads or applies the header. No
  authentication of the header.
- No change to the canary or the `@smoke` Cucumber steps. Both already send
  the header.
- No fix for the in-memory counter's shared dedupe map, where a synthetic and
  a real request with the same idempotency key collide. The in-memory counter
  is used only locally and in tests. That fix belongs to a separate change.
- No correction to the `docs/observability.md` claim that the canary checks
  p95 < 300 ms.
- No new requirement covering server-side isolation of synthetic counts. The
  shared counter contract spec already tests it. Moving it into
  `synthetic-traffic` can happen later.
