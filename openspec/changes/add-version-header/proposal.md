# Proposal

## Why

Black-box clients (smoke tests, monitors, on-call engineers) cannot currently tell
which build of greeter-http, or which greeter-core, is serving a request. The
version is only visible in logs and the local startup banner. Exposing it on
every response makes "what is deployed?" answerable with one `curl -i`.

## What Changes

- Every response produced by the Rack app carries `X-Greeter-Version`
  (`GreeterHttp::VERSION`, no leading "v", e.g. `0.5.20`) and
  `X-Greeter-Core-Version` (`Greeter::Core::VERSION`).
- Values come only from the two constants, never from request input or
  environment variables.
- The headers are added in one place (a Rack middleware wrapped around the Rack
  app in the composition root) so no route or error path can omit them.
- The Lambda handler passes them through to API Gateway unchanged.
- A request carrying `X-Greeter-Synthetic: true` gets the same response as
  without it; the header is accepted, not echoed.
- A `@smoke` Cucumber scenario checks both headers on a deployed stage.
- `GreeterHttp::VERSION` is bumped from `0.5.19` to `0.5.20`.

No existing status code, body, or error code changes.

## Capabilities

### New Capabilities
- `version-headers`: Version-identification response headers present on every
  response the function produces.

### Modified Capabilities
<!-- none: greeting-counter requirements are unchanged -->

## Impact

- Repos touched: `greeter-http` only. **greeter-core is not affected** (only its
  existing `Greeter::Core::VERSION` constant is read).
- Code: new `lib/greeter_http/adapters/version_headers.rb`;
  `lib/greeter_http/app.rb` (composition root wiring);
  `lib/greeter_http/version.rb` (bump).
- Tests: `spec/adapters/version_headers_spec.rb`,
  `spec/adapters/lambda_handler_spec.rb`, `spec/app_spec.rb`,
  `features/` (new feature plus `@smoke` scenario and steps).
- Docs: README/docs mention of the headers.
- No infra, IAM, or dependency changes.

## Non-goals

- Responses generated by API Gateway itself (e.g. its own 404 for unrouted paths
  without invoking the function) are out of scope.
- No new routes, status codes, or error codes. Notably the Rack app does not
  produce 405 or 415 today (wrong method or path returns 404); this change does
  not add them.
- No version endpoint, no version in the response body, no changes to logging.
- No CORS `Access-Control-Expose-Headers` change.
