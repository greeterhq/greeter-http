# Spec Delta

## Purpose

Lets black-box clients see exactly which greeter-http and greeter-core versions
are deployed by reading two headers on every response the function produces.

## ADDED Requirements

### Requirement: Successful greetings carry version headers
The system SHALL include `X-Greeter-Version` (the service version without a
leading "v") and `X-Greeter-Core-Version` (the greeter-core version) on every
successful greeting response.

#### Scenario: Created greeting carries both headers
- **WHEN** a client sends a valid greeting request with a fresh idempotency key and the system responds `201 Created`
- **THEN** the response has `X-Greeter-Version` equal to the service version and `X-Greeter-Core-Version` equal to the greeter-core version

#### Scenario: Replayed greeting carries both headers
- **WHEN** a client repeats a greeting request with the same idempotency key and name and the system responds `200 OK`
- **THEN** the response has both `X-Greeter-Version` and `X-Greeter-Core-Version` with the same values as on the `201`

### Requirement: Rejected requests carry version headers
The system SHALL include both version headers on every rejection response,
without changing the status code or body of that response.

#### Scenario: Malformed or missing-key request carries both headers
- **WHEN** a client sends malformed JSON, or omits the idempotency key, and the system responds `400 Bad Request`
- **THEN** the response has both version headers

#### Scenario: Key reuse carries both headers
- **WHEN** a client reuses an idempotency key with a different name and the system responds `409 Conflict`
- **THEN** the response has both version headers

#### Scenario: Oversized body carries both headers
- **WHEN** a client sends a body larger than the cap and the system responds `413`
- **THEN** the response has both version headers

#### Scenario: Invalid name carries both headers
- **WHEN** a client sends an invalid name and the system responds `422 Unprocessable Entity` with error `invalid_name`
- **THEN** the response has both version headers

### Requirement: Storage failures carry version headers
The system SHALL include both version headers on a `503` response caused by
transient storage failure, in addition to its `Retry-After` header.

#### Scenario: Storage unavailable carries both headers
- **WHEN** storage is transiently unavailable and the system responds `503` with `Retry-After`
- **THEN** the response has both version headers and still has `Retry-After`

### Requirement: Unrouted requests carry version headers
The system SHALL include both version headers on every response for a path or
method that the Rack app does not route. Responses generated by API Gateway
without invoking the function are out of scope.

#### Scenario: Unrouted path carries both headers
- **WHEN** a client requests a path other than `POST /greetings` (for example `GET /nope`) and the system responds `404`
- **THEN** the response has both version headers

#### Scenario: Unsupported method on the greetings path carries both headers
- **WHEN** a client sends `GET /greetings` and the system responds `404`
- **THEN** the response has both version headers

### Requirement: Unexpected errors carry version headers
The system SHALL include both version headers on a `500` response produced when
an unexpected exception is mapped to an error response.

#### Scenario: Unexpected exception carries both headers
- **WHEN** an unexpected non-storage exception is raised while handling a greeting and the system responds `500` with error `internal_error`
- **THEN** the response has both version headers

### Requirement: Version header values are fixed by the build
The system SHALL derive both header values only from the service and
greeter-core version constants, never from request input or environment
variables.

#### Scenario: Request input cannot change the values
- **WHEN** a client sends request headers named `X-Greeter-Version` or `X-Greeter-Core-Version` with arbitrary values
- **THEN** the response headers carry the build's constant values, not the supplied ones

#### Scenario: Environment cannot change the values
- **WHEN** the process environment defines variables such as `GREETER_VERSION`
- **THEN** the response headers still carry the build's constant values

#### Scenario: Inner application value is overwritten
- **WHEN** the wrapped application itself returns different `X-Greeter-Version` or `X-Greeter-Core-Version` values
- **THEN** the response headers carry the build's constant values

### Requirement: Version headers disclose nothing beyond the two versions
The system SHALL refuse to start if either version value is not a plain
dotted version (digits and dots, with an optional alphanumeric pre-release
suffix) and SHALL NOT add any other header that discloses component versions.

#### Scenario: Malformed version value is rejected at startup
- **WHEN** the application is composed with a version value containing a leading "v", whitespace, or a line break
- **THEN** composition fails with an error and no response is ever produced with that value

#### Scenario: No other version-disclosing headers
- **WHEN** a client receives any response
- **THEN** the response has no `Server`, `X-Powered-By`, or other header naming Ruby, Rack, or gem versions

### Requirement: Synthetic marker does not alter version headers or responses
The system SHALL accept `X-Greeter-Synthetic: true` on any request, SHALL NOT
echo it in the response, and SHALL return the same status, body, and version
headers as for the same request without it.

#### Scenario: Synthetic request matches non-synthetic response
- **WHEN** a client sends a request with `X-Greeter-Synthetic: true`
- **THEN** the response status, body, and version headers equal those of the same request without it, and the response has no `X-Greeter-Synthetic` header

### Requirement: Lambda handler preserves version headers
The system SHALL deliver the version headers unchanged to API Gateway in the
Lambda response.

#### Scenario: Handler passes headers through
- **WHEN** the Lambda handler processes an API Gateway event for any routed or unrouted request
- **THEN** the returned `headers` map contains both version headers with the same values the Rack app produced

### Requirement: Deployed stage exposes version headers
The system SHALL expose both version headers on a deployed stage, verifiable by
a smoke test.

#### Scenario: Smoke check on a deployed stage
- **WHEN** a smoke test posts a valid greeting to the deployed base URL
- **THEN** the response has `X-Greeter-Version` matching `\d+\.\d+\.\d+` without a leading "v" and a non-empty `X-Greeter-Core-Version`
