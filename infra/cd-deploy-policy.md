# CD deploy role policy

`infra/cd-deploy-policy.json` is the least-privilege permissions policy for the
CD OIDC role **`greeter-http-cd-deploy`**. It grants exactly what `sam deploy`
of `infra/template.yaml` needs for the `greeter-http-dev` and
`greeter-http-prod` stacks, plus the `aws-sam-cli-managed-default` bootstrap
stack and its packaging bucket.

## Attach it

```bash
aws iam put-role-policy \
  --role-name greeter-http-cd-deploy \
  --policy-name greeter-http-cd-deploy \
  --policy-document file://infra/cd-deploy-policy.json
```

(The `.json` is a pure IAM policy document — no comments — because
`put-role-policy` rejects any top-level key other than `Version`/`Id`/
`Statement`. The rationale lives here instead.)

## Scoping rationale

Where an AWS API supports resource-level ARNs **and** the physical name is
predictable, statements are scoped to those ARNs:

- **CloudFormation** — the two stack ARNs + the SAM managed bootstrap stack,
  plus the AWS-owned `transform/Serverless-2016-10-31` macro ARN. Deploying a
  SAM template runs that transform to expand `AWS::Serverless::*` resources, and
  CloudFormation checks `CreateChangeSet` against the transform resource as well
  as the target stack. The ARN lives in the `aws` account namespace (not ours),
  so the stack-scoped ARNs don't cover it; it is named explicitly, not
  wildcarded.
- **DynamoDB** — tables named `greeter-http-{dev,prod}-*`.
- **IAM roles** — roles named `greeter-http-{dev,prod}-*` (SAM creates the
  function execution role and the canary role; `PassRole` is scoped the same).
- **S3** — the SAM packaging bucket and the per-stack canary-artifacts buckets.
- **SNS** — topics named `greeter-http-*`.

Several services either do not support resource-level permissions on their
*create* actions, or the physical resource name is generated by CloudFormation
and unknown ahead of time. For these, access is scoped by **action** (only the
verbs a deploy needs) with `Resource: "*"` — deliberate, not an oversight:

- **Lambda, API Gateway v2, Synthetics, CloudWatch alarms, CloudWatch Logs, KMS.**

Tighten these to ARNs once the physical names are stable if you want a second
hardening pass.

The **KMS** statement carries both control-plane and data-plane actions. The
control-plane verbs (`CreateKey`, `PutKeyPolicy`, rotation, aliases, tagging)
create and manage the key. The data-plane verbs (`Encrypt`, `Decrypt`,
`GenerateDataKey`, `GenerateDataKeyWithoutPlaintext`) are needed at deploy time
because the Lambda has encrypted environment variables: CloudFormation creating
the function makes Lambda call `kms:Encrypt`/`GenerateDataKey` as the *deploying*
principal to wrap those vars, and `kms:CreateGrant` to let the function's
execution role decrypt them on cold start without editing the key policy.
`ListGrants`/`RevokeGrant` cover the grant's lifecycle on stack update/delete.
Without these the key is created but the function create fails with a KMS
`AccessDenied` (first on `Encrypt`, then on `CreateGrant`).

## Caveats

- **Not yet proven by a real deploy.** This policy was derived from the resource
  types in `template.yaml`, not validated against a live `sam deploy`. SAM /
  CloudFormation sometimes call more actions than expected; the first dev deploy
  is the real test. If it fails with `AccessDenied` on a specific action, add
  that action here and re-attach. Expect possibly one such iteration.
- **It can create IAM roles** (SAM needs this). That makes the CD role
  privileged; the ARN scoping on `iam:*Role*` to `greeter-http-*` names is what
  keeps it from being able to mint arbitrary roles. Review changes to the IAM
  statement with that in mind.
- **`AWS::IAM::Role` creation requires `CAPABILITY_IAM`** (and named roles would
  need `CAPABILITY_NAMED_IAM`). The CD workflow passes `--capabilities
  CAPABILITY_IAM`; keep that in sync if the template starts creating
  named/explicit-ARN roles.
